# Parity harness

Differential testing: runs the Rust engine and the Java Forge engine on the same deck/seed and compares decision-by-decision. The home base for parity bug investigation.

Read first: `/AGENTS.md`, `docs/agents/ENGINE_BUGFIX_WORKFLOW.md`, `docs/PARITY_TESTING.md`.

## Deck directories

Deck names passed via `--deck1` / `--deck2` resolve from two folders in order:

1. `parity_decks/` — canonical home for decks referenced by `regression.json`. Land new regression decks here.
2. `public/preset_decks/` — wider preset library shared with the web build (UI, `yarn import-deck` landing zone). Decks here are still resolvable by name for ad-hoc parity runs.

Both engines share this lookup: the Rust list lives in `runner::DEFAULT_DECKS_DIRS`; the Java harness reads it via `-Dpreset.decks.dir=parity_decks,preset_decks` (set automatically by `java_bridge::decks_dir_property`). `--decks-dir <path>` still overrides with a single explicit folder for tests/debugging.

## Common workflows

### Reproduce a divergence

```bash
yarn parity <test-name>
# verbose:
yarn parity:test -- --deck1 <d1> --deck2 <d2> --seed <N> --max-turns 30 -v
```

Trace flags: `FORGE_RNG_TRACE=1` (both engines), `FORGE_TRIGGER_TRACE=1`, `FORGE_STACK_TRACE=1`, `FORGE_ZONE_TRACE=1` (Rust only, free text on stderr). See `docs/PARITY_TESTING.md` for the full env-var list.

When a card is offered by one engine and not the other, run the Rust game with `FORGE_CARD_TRACE=<card name>`. Besides the card's zone moves, every priority prints one line per copy in hand, graveyard, exile or command zone (`GameLoop::trace_playability`, after `get_playable_cards`): the modes offered, then the checks that decide them, recomputed: `CantBeCast`, the spell timing check, instant speed and flash, minimum targets and whether candidates exist, the printed cost and the adjusted one, the mana counted for this spell with `RestrictValid$` applied, whether the pool and the payment simulation can pay, and the statics that grant MayPlay. Each non-mana activated ability prints `offered` or the check that refused it (`activation_verdict` in `get_activatable_abilities`). A cast of the card that is undone after it reached the stack prints `cast of <name> rolled back at cast_spell.rs:<line>`, the exit that undid it (the agent only sees `Card play failed`). The checks are recomputed for the normal cost only, so an alternative cost that is offered while `simulated_pays=false` is expected. Under `--mana-probe forge` each run of the ported `ComputerUtilMana` probe also prints its steps (`probe:` lines: the shard, the source, the mana it makes, what is left unpaid). The same variable reaches the JVM as `-Dforge.parity.card.trace`, and the harness `ActionSpace` prints `[card-trace-java]` lines: for each of the card's abilities, `offered` or the first check that dropped it (`getAllPossibleAbilities`, `canPayManaCost` with the mana cost, valid targets, `checkRestrictions`). Java has no step trace for its mana check. While the variable is set the Java cache is not read, so the JVM runs every game. For a card that is the host of a trigger, each event of a mode one of its triggers listens for prints a `[trigger-trace]` line: `runs`, the first check `TriggerHandler::trigger_run_check` failed (`requirements`, `zone`, `perform_test`, `activation limit`, ...), or `not active` when the trigger was not in the active list the event was matched against. No line at all for the mode means no such event was run.

The comparator stops at the first divergent snapshot and records every differing field of it: the headline is `first_divergence`, the full list is `divergences`, and the text report prints the rest as `also ...` lines. Battlefield cards are paired by name, so one extra permanent shows up once as `battlefield.cards` and per-card fields carry the card name. Nothing after that snapshot is compared, so a field that is absent from the list agreed only up to that point. A failed run carries a verdict: `FAIL` for a state divergence, `ABORTED` or `TIMEOUT` when a parity guard stopped the Rust game before Java finished, `OOM` or `ERROR` for harness failures. Every compared matchup also carries `decision`: the first agent callback the engines disagree on (`src/decision_diff.rs`), with the last callback they agreed on as context. It is usually a turn earlier than the state divergence and names the cause: a prompt Java raises and Rust never does, or an action space that offers different options. A matchup can pass on state and still have one; `gate-diff` prints how many matchups agree on both. The Java controller writes two rows under one name for `confirm_action`, `confirm_payment` and `choose_binary` (the pick, then the description) where Rust writes one; `is_java_pick_row` drops the Java pick row before either callback comparison, and a new boolean prompt in `DeterministicController` must be added there. `$ACTION_SPACE` and `choose_action` are compared by the sequence of `name@id` cards on offer, not by their text: Java prints any ability that is not an activated ability (Plot's special action) as `CastSpell`, and its `ability_index` counts the abilities currently possible while Rust's counts the card's ability list, so the kind and the index never line up. A different card sequence is a different option set, a different order, or a different pick. The Rust log names a callback after the agent method, except where Java reaches the same decision through a general prompt: the legend rule's `choose_legend_keep` is logged as `choose_single_entity_for_effect`, which is what `GameAction.handleLegendRule` asks (`runner.rs`, the logging-agent method table). Two pairs of names are compared as equal (`decision_diff::canonical_name`): a discard paid as a cost is `choose_discard` in Rust and `choose_cards_for_effect` in Java, because `HarnessCostPlumbing` routes `CostDiscard` through `chooseCardsForEffect`; and an announced value (X, `Announce$`) is `choose_number` in Rust and `announce_requirements` in Java. Both agents make the same draw. A Java `announce_requirements` row with outcome `null` (empty bounds, nothing asked) is dropped (`is_java_unasked_announcement`), since Rust asks nothing there. Callbacks after the turn limit are dropped on both sides: Forge runs the next turn's untap step before the harness ends the game, so Java logs its optional-untap prompts where Rust has already stopped. A `choose_single_replacement_effect` or `choose_counter_type` row with exactly one option is dropped on both sides (`is_forced_choice`): Forge asks even when one replacement applies or one counter type is listed, no RNG is drawn, and Rust applies some of those rules inline (`K:etbCounter`, stun counters), so the row said nothing about a decision and hid every later one. A pick among two or more is still compared. `pay_cost_to_prevent_effect` is not a compared callback: Java logs it after the nested payment prompts (and logs `false` when the cost cannot be paid), Rust logs it before paying and skips it when the cost cannot be paid, and neither draws RNG for it; the prompts inside the payment are compared as usual. `pay_combat_cost` is left out for the same reason: Java's `payCombatCost` pays an attack tax through the plumbing (a `pay_mana_cost` row) and logs its result after, where the Rust agent answers `CombatCostAction::AutoPay` first and the engine then pays through the same mana session, so the `pay_mana_cost` rows line up and the result rows do not. A face-down card is printed as `@id` with no name in every Rust callback row (`FmtCtx::card`), as Java's `getName()` is empty for it. `chooseTargetsFor` sorts its candidates by the string `ParityOrder.targetSortKey` (`"1|" + name + "|O" + owner + "|C" + controller + "|I" + id`), compared whole, so a face-down card sorts after every named one and a name sorts after any name it is a prefix of; `DeterministicAgent::target_sort_key` builds the same string for every target sort, where a tuple sort would put both first. A split or Room card outside the battlefield is printed by its combined `A // B` name for the same reason: its current state is `Original`, so that is what Java's `getName()` returns, and only on the battlefield does an unlocked door make one face current. `FmtCtx::card` and the agent's own `card_names` snapshot (`deterministic_agent.rs`, which is where the `$ACTION_SPACE` rows take their names) both apply this rule and have to stay in step. `--localize` (matrix mode and `--deck1/--deck2 --seeds`) reruns each failing matchup with `--deep`, reports where that run first diverges, and prints what each engine did since the last matching snapshot (zone moves, life, taps, counters, stack), the decisions each took there, and the Forge game events the Java harness recorded in that window (`EventRecorder`, deep runs only; Rust has no such stream, so events are shown and never compared). `PARITY_ALL_DIVERGENCES=1` still prints the list as `[all-div]` lines on stderr. `--repeat-check` runs the Rust game twice on the same seed and reports the first differing log entry, which separates nondeterminism from a real divergence. `--callback-compare` also compares the agent callback sequence (acting player and prompt name, not the answer) inside each snapshot window. Game-state fields are compared before the RNG call counts, because the counts diverge whenever the engines make different decisions.

### Gate a change on the Standard survey

```bash
yarn parity:survey       # scripts/survey-gate.sh; needs target/parity/parity and the harness jar
```

Runs `--matrix --matchups survey_matchups.tsv --seeds 42 --max-turns 20 --gate-out <file>` and hands the result to `parity gate-diff survey_baseline.jsonl <file>`, which prints `GATE_SAME`, or one line per changed matchup and `GATE_CHANGED`; the script then prints `SURVEY_SAME` or `SURVEY_CHANGED` and exits 0 or 1. The classes are `FIXED`, `REGRESSED`, `MOVED_LATER` and `MOVED_EARLIER` (same status, the divergence turn moved), `CHANGED` (same turn, different field or verdict) and `NEWLY_VISIBLE`: the headline field is one the baseline's comparator did not check, so the divergence became observable rather than being introduced. The gate file header records the compared-field list (`comparator::COMPARED_FIELDS`, keep it in sync when adding a snapshot field) and the build that produced it. A fix that moves a divergence later shows as `MOVED_LATER`; only closing the last gap shows as `FIXED`. When a change is meant to alter the baseline, copy the observed file the script names over `survey_baseline.jsonl` and commit both together. Every run is copied to `.parity-history/<utc>-<sha>.jsonl`, so two past runs can be compared with `gate-diff` as well. `PARITY_PROFILE` (default `parity`, binary at `target/<profile>/parity`), `PARITY_BIN`, `PARITY_JAR`, `JAVA_WORKERS`, and `JAVA_HEAP` override the defaults. The script exits 2 when the binary, the jar, or the cardset archive is missing or the run produced no matchup lines; in a git worktree it falls back to the main checkout's `src-tauri/resources/cardset.rkyv`. It prints the binary, commit and dirty flag it ran, then the Java cache hit count and the per-stage totals.

The parity binary mmaps `src-tauri/resources/cardset.rkyv` at startup. `yarn parity` ensures it's present, but direct invocations (`cargo run -p parity …`, manual `./target/parity/parity …`, custom CI jobs) need to materialise it first — see `manabrew-engine/AGENTS.md` § "Cardset archive". A bare `cargo build` of this crate doesn't build it.

Parity workflows build with `--profile parity` (release + `debug-assertions`), output dir `target/parity/`, so the dual-evaluation drift guards in the engine stay active during parity runs. For the edit-build-gate loop use `--profile parity-dev` (`opt-level = 2`, no LTO, incremental, `debug-assertions`), output dir `target/parity-dev/`: a one-file engine edit rebuilds without the fat-LTO link, and the survey gate gives the same result under both profiles. Compiled-vs-legacy selector drift is reported as `[selector-drift]` lines (once per selector); set `FORGE_SELECTOR_ASSERT=1` to make it panic at the divergence site instead.

### Read a finished run

```bash
parity --java-jar <jar> --matrix --matchups <file> --seeds 1,2,3 --gate-out run.jsonl --format json -o run.json
parity gate-summary run.jsonl [--decisions]      # tally, per-pairing PASS counts, every non-PASS game
parity gate-summary run.jsonl --group            # the same games clustered by first differing field and by decision
parity explain run.json --seed 74 --deck2 izzet  # one game; without --seed, every game that failed or has a decision difference
parity explain run.json --seed 74 --turn 12 --player 1          # both logs' callback rows of one turn
parity explain run.json --seed 74 --around "Emeritus@31" --rows 60   # both logs from the first row that mentions a card
parity why run.json --seed 74 --deck2 izzet      # rerun to the decision turn with the card trace on the one-sided cards
```

`gate-summary` needs no baseline and exits 1 if any game is not `PASS`; `--decisions` also lists the games that agree on state only. `explain` (`src/explain.rs`) prints five things for a game, all from the report, with no rerun. The first RNG draw the two agents disagree on, keyed by draw kind, option count, result, turn and player, and for `choose_action` also by the picked card (its `name@id`, without the ability index), so the same index into a differently ordered list counts; one-option and zero-option picks (neither draws) and Rust's summary rows (`pick_many_unique`, and one named after its callback, as `choose_colors` logs) are left out, and `pick_one` reads as `pick_index`. The first target prompt whose candidate list differs, with the candidates only one side offered: both agents log a `choose_targets_for(candidates)` row before every target pick (Rust in `DeterministicAgent::log_target_candidates`, which never assigns a parity id, so a card first seen there prints as `Name@?`), `decision_diff` does not compare it, and Java lists the candidates in game order where Rust sorts them, so the lists are compared as sets. Every snapshot field that differs at the divergence turn, with unequal card lists reduced to the names only one side has. The options that differ in the first unequal `$ACTION_SPACE` of the decision's phase, as `name@id`, or `name@id ability` for an activated ability (the index is left out, since the engines number abilities differently). The callbacks of that phase on each side. The draw diff usually names the cause a turn or more before the state diverges: an extra or missing prompt, or an option only one engine offers. When the draws agree to the end and the state still differs, the cause is deterministic (a static, a counter, a trigger), and the snapshot diff is the place to look.

`--turn N` (with `--player P` and `--phase NAME` to narrow it) or `--around TEXT` prints a window of each log's callback rows instead of those five things: every row of the turn, or `--rows` rows (default 40) from `--context` rows before the first one whose name or outcome contains `TEXT`. Priority passes, `$ACTION_SPACE` rows and Java-only rows are left out unless `--all`. Each side is anchored on its own first match, and the same card can be named differently in the two logs at the same moment (a transformed card's other face, a prompt only Java raises), so anchor on `name@id` and combine with `--turn` when the first mention is not the one you mean.

`why` reruns each selected game (with `--java-jar`, default `forge-harness/target/forge-harness-jar-with-dependencies.jar`) to its decision turn, once per card that only one engine offers in the first differing action space of the decision's phase (a phase where one engine logged no action space counts as an empty one) or `--card NAME`, with `FORGE_CARD_TRACE` set, and prints the `[card-trace]` and `[card-trace-java]` lines of that turn and player, repeated lines collapsed. It prints the command it ran; arguments after `--` go to the rerun (`-- --mana-probe autopay`, `-- --deep`), since the report does not record the flags of the original run. A decision that is not an action space difference (`Rust choose_action / Java choose_attackers`) has no one-sided card, so pass `--card`.

`gate-summary --group` replaces the per-game list with two clusterings. Failures are grouped by verdict and first differing field, with a count of the card names that only one side's value holds across the group (the per-card field's card for fields like `battlefield[i].tapped`). Games with a decision difference, `PASS` included, are grouped by the callback each engine logged there (`Rust $ACTION_SPACE / Java choose_action`). Gate files keep 200 characters of each decision, too few to compare option lists, so the decision groups go by callback only; `explain` has the lists.

### Probe one card, or shrink a failing matchup

```bash
parity --java-jar <jar> --probe "Flock Impostor" --seeds 42,43,44 --max-turns 14
parity --java-jar <jar> --probe-file names.txt --probe-out card_parity.tsv --probe-reports reports/
parity --java-jar <jar> --deck1 survey_g390 --deck2 survey_g391 --seed 42 --max-turns 8 --shrink
```

`--probe` (`src/probe.rs`) builds a deck of 12 copies of the card, `--probe-partners` (two cheap colourless creatures by default, so auras, equipment and pump have something to land on) and 24 basic lands split across the card's colour identity, and plays it against `--probe-opponent` on each seed. A card is `PASS` only if every seed passed, the card was cast or played in at least one of them, and the engines took the same decisions throughout; `PASS_STATE` means the snapshots agreed while the decision sequences did not (the `decision` column says where), so the agreement may not survive another seed; `NEVER_USED` means the run could not have observed it, `DIVERGES` names the seed, turn, field and card, `UNBUILDABLE` means the name is not in the card database. "Used" is every name the card can be logged under (`probe::coverage_names`): the name asked for, the real name behind a `Variant:UniversesWithin:FlavorName:` alias, and both faces of a split card, counted from a cast, a land drop or the source of an activated ability. Without that a Universes Within name, whose game logs the card it resolves to, and a card only used through an ability were `NEVER_USED` whatever they did. Results come from the same Java cache as every other mode, so reprobing after an engine change reruns only Rust. `--probe-reports <dir>` writes the usual single-matchup JSON report for every seed that does not pass or passes on state with a differing decision, as `<card>-<seed>.json`, so `explain` and `why` work on a probe failure straight away; a probe deck is also a valid `--deck1` as `inline:<Card>*12|Memnite*4|Bronze Sable*4|<Basic>*24`.

`--shrink` rebuilds both decks as inline specs and removes non-basic cards (replacing them with the deck's most common basic land, so deck sizes hold) while the matchup still has verdict `FAIL`, then prints the smallest pair as a ready-to-run command. The surviving divergence can be a different one from the original: read the headline it prints.

### Ask the card scripts a question

```bash
parity query --api Dig --param Tapped --cards-file standard_names.txt
parity query --mode ChangesZone --param ValidCard --value Creature.Other --show 5
parity query --keyword Web-slinging
parity coverage --matchups manabrew-rs/crates/parity/survey_matchups.tsv --cards-file standard_names.txt
parity coverage --decks red_burn,green_stompy --cards-file standard_names.txt
parity card "Crystal Fragments" "Bonesplitter"
```

`--cards-file` takes a plain list of card names, one per line, `#` for a comment (`script_index::read_card_list`). No such file is checked in and nothing generates one; `standard_names.txt` above is whatever list you hand it. Forge's own definition of Standard is `forge/forge-gui/res/formats/Sanctioned/Standard.txt`: a `Sets:` line of 19 set codes and a `Banned:` line of 13 names. Resolve each code against the `Code=` line of a file in `forge/forge-gui/res/editions/` and take its `[cards]` section (`<collector#> <rarity> <name> @<artist>`; the later sections are variants and tokens). That union is 4,630 printed names, of which 6 are basics and 28 are split `A // B` names. Do not probe basics, and remember that an edition of `Type=Online` such as `OM1` is not Standard: its names are `Variant:UniversesWithin:FlavorName:` aliases of cards already in the pool, so probing them re-probes cards you already cover under another name.

`query` (`src/script_query.rs`) filters the parsed script lines of every card (or of `--cards-file`) by API, trigger or static `--mode`, replacement `--event`, `--param`, `--value` substring, `--keyword` and `--kind`, prints matching cards with their lines, and says which engine files contain the parameter or API as a string literal. Use it instead of grepping `cardsfolder`: `$` and `|` in a pattern make a text search match nothing without saying so. Each answer carries its own control: the number of cards scanned, how many carry `ValidTgts$` (zero aborts with an error), and how many match the API filter alone, so a zero for the full query means the parameter is absent and not that the search failed.

`parity card <name>...` (`src/card_dump.rs`) prints what `Card::from_rules` builds from a card script, or the template a token script (`sword`, `r_1_1_warrior`) gives: type line and cost, keywords, every activated ability with its index, API and activation zone, triggers, statics, replacement effects, SVar names, and the other face. Use it when an engine never offers or never fires something the script has: a keyword with no ability behind it shows up here without running a game.

`parity selector <text>...` prints the compiled selector IR for a `Valid$`-style string, so a property that was dropped, merged or lowered to a subtype is visible without a game.

`parity selector-audit` (`src/selector_audit.rs`) compiles `Card.<name>` for every name Java's `CardProperty` tests with `property.equals`, and lists the ones the engine's selector compiler lowers to a subtype, with how many card scripts use each. A property lowered that way never matches (it is looked up as a type), where Java checks it first and falls back to types only at the end. Teach the compiler (`parsing::lower_selector_part`) or the legacy matcher the property, then rerun the audit.

`coverage` lists the APIs, trigger modes, replacement events and keywords of the pool that no deck in a gate carries. A gate result says nothing about those, whatever it prints.

### Sweep a card list for panics, loops and hangs

```bash
parity sweep --cards-file standard_names.txt --out-dir sweep-out --games 10 --max-turns 30 --census-out census.json
parity sweep-deck --deck "<inline spec>" --seeds 3 --max-turns 30     # replay one game; repro.txt has the exact line
```

`sweep` (`src/sweep.rs`) is Rust-only random play: cards grouped by colour identity into decks of `--chunk` cards, `--games` seeds each. Every deck runs in its own child process, so a game that never returns is sampled (`sample <pid>`, macOS) and killed after `--game-secs` + `--kill-after-secs` without stopping the run, and a panic cannot leak thread-local state into later games. Game statuses: `OK`, `PANIC` (message and location), `LOOP` (the same state fingerprint came back 200 times within a turn at a decision point; the detail lists the last actions), `BUDGET` (`--decision-budget` decisions with no repeated state), `TIMEOUT`, `KILLED`. Agent seeds come from the deck contents and the seed, not from the deck's position, so each line of `repro.txt` replays its game alone. `games.tsv` and `cards.tsv` are written in deck order and are the same for the same inputs. With `--census-out` the per-deck censuses are merged, which gives the census a much wider reach than the survey.

### Find what the engine ignores

```bash
parity --java-jar <jar> --matrix --matchups <file> --census-out census.json ...   # any mode that plays games
parity census-report census.json --cards-file standard_names.txt
python3 scripts/parity-ir-audit.py --cards-file standard_names.txt
```

`--census-out` turns on `manabrew_engine::census` for the run. `census-report` joins it with the parsed card scripts (`src/script_index.rs`) and prints, weighted by how many of the named cards are affected:

- script parameters with no matching string anywhere in the engine sources. These are certain gaps. The report refuses to run if it cannot find `"ValidTgts"` in the engine sources, so an empty list never means "looked in the wrong place".
- parameters the engine knows, carried by abilities the run consulted, and never read through a tracked accessor. Candidates only: a builder that reads `Params::inner()` directly is not tracked.
- APIs, trigger modes and replacement events the run never exercised, so it says nothing about them.
- permissive fallbacks that fired (`property-as-subtype`, `condition-assumed-true`, `valid-player-matches-all`, `count-expression-as-zero`, `alter-attribute-ignored`, ...) with the offending string, real subtypes filtered out against `TypeLists.txt` and core types and supertypes filtered out by name (`Card::has_string_type` answers those, as Forge's `CardType.hasStringType` does).

`scripts/parity-ir-audit.py` covers the case the census cannot see: a parameter parsed into an `*Ir` field that no effect ever reads.

### Compare two commits, or bisect

```bash
yarn parity:ab ab <revA> <revB>          # WORKTREE stands for the working tree as it is
yarn parity:ab bisect <good> <bad>
yarn parity:ab bisect <good> <bad> --deck1 "inline:..." --deck2 <deck> --seeds 42 --max-turns 14
yarn parity:ab baseline                   # refuses a dirty tree
```

`scripts/parity-ab.mjs` builds each commit once into `target/parity-bins/<sha>/parity` from a detached checkout, so a binary labelled with a SHA is that SHA's source. Both sides run the survey matchups (`--matchups`, `--seeds`, `--max-turns` override) and the two gate files go through `gate-diff`. A binary that predates `--gate-out` is run with `--format json` and converted. With `--deck1`/`--deck2` (deck names or `inline:` specs) each side runs that one matchup instead, a game per seed in single-game mode, which every commit's binary has, and is converted the same way; bisecting a repro over eight commits builds four. Use this instead of reverting a change and rerunning by hand: a matchup that differs between a commit and its parent is attributable to that commit, and one that does not is not.

### Java result cache

`src/java_cache.rs` stores each matchup's full Java log under `.parity-cache/`, so a hit runs only the Rust game. The whole cache is wiped when the source hash changes: the harness and Forge Java sources, the card and token scripts, and the harness jar. Each entry is keyed on the matchup parameters plus the contents of its two decks, so editing or adding a deck invalidates only the matchups that use it. Java workers start on the first cache miss (`JavaServerPool::lazy`), up to `--java-workers`; a fully cached run starts none. The default worker count (`max_workers_for_memory`, every mode but a single `--deck1`/`--deck2` matchup) is how many JVMs fit in RAM at `--java-heap`, capped at `available_parallelism()` and 8, which counts efficiency cores as if they were performance cores and so oversubscribes an Apple Silicon machine. A cold probe of 32 cards over 4 seeds at 20 turns on a 4+6-core 24 GB M-series took 35s at `--java-workers 3`, 39s at 4, 47s at 5 and 61s at the default 8; measure before trusting the default on a heterogeneous CPU. A Java game that runs longer than `PARITY_JAVA_GAME_TIMEOUT_SECS` (default 300, `0` turns it off) has its worker killed (`GameWatchdog` in `java_bridge.rs`); the matchup fails as a crashed worker and the pool spawns a new one, so one Forge game that never ends (Stream of Thought on seeds 42 and 43) no longer stalls a probe or a gate. The Rust side has no such guard: a Rust game that overflows its stack aborts the whole run (no thread can catch it), and one that never ends stalls it at the last few cards. When a probe dies or stops advancing, list the names its `[probe] [n/N]` lines never reached and probe them one at a time to find the card.

### Measure the Rust side

With the Java cache warm, a gate's time is the Rust games. `cargo bench -p parity --bench game` (`benches/game.rs`) runs one 30-turn game per first-matchup pairing through `run_with_data`, with the same agents, snapshots and log as a gate; `[profile.bench]` matches `parity-dev`, so it builds incrementally. Save a baseline before a speed change (`-- --save-baseline before`) and compare after (`-- --baseline before`). For where the time goes, macOS `sample <pid> 8` on a running `parity` process gives a call tree per thread.

For self-play throughput without the parity agent, snapshots or Java, build `cargo build --profile selfplay -p parity --example selfplay` and run `RAYON_NUM_THREADS=1 target/selfplay/examples/selfplay <deck1> <deck2> <games> <max_turns> <play_weight> [first_seed]` from the repo root (deck specs as for `--deck1`); games use seeds `first_seed..first_seed+games`, so one game replays alone. It prints games/s, decisions/s, setup time per game and a checksum of every game's winner, final turn and life totals; the engine is deterministic, so a refactor that should not change play must leave the checksum unchanged, at any thread count. The `selfplay` profile is opt-level 3 with fat LTO: `release` is `opt-level = "z"` for the app's size, and random self-play runs about 1.8x faster under `selfplay`; the example also uses mimalloc, as the `parity` binary does, worth another 1.18x on one thread. `GameLoop::game_rng` defaults to `ThreadRngAdapter` (`rand::thread_rng`), so any driver outside the parity runner must install a seeded `GameRng`, as the example does, or in-game shuffles and random picks differ from run to run. An agent that accepts every optional replacement can loop without end: Superior Spider-Man's optional Mind Swap copying another Superior Spider-Man brings a new Mind Swap with a new effect id, which `ReplacementHandler` offers again, as Forge's does (`hasRun` is per effect id). The trait default accepts, so the run recursed until the stack overflowed; the example declines a replacement prompt that repeats its source and question since the agent's last priority decision. `parity sweep`'s agent still takes the default, and any RL agent needs the same bound.

Every agent decision snapshots the game (`snapshot_state`). `DeterministicAgent` keeps one shallow `GameState` (players, cards, zones, stack, turn) and refreshes it in place with `Card::refresh_parity_snapshot`; `CapturingAgent` reads that same state through `snapshot_game()`. A snapshot card has no parsed triggers, abilities or replacement effects, its other face has none either, and only a card in a static-ability source zone (`ZoneType::is_static_ability_source`) keeps its static abilities (the agent reads them for block restrictions), copied by `StaticAbility::clone_for_parity_snapshot` with an empty base, so a snapshot static has no param maps. If an agent starts reading more of a card, add it back there. A refresh copies a field only when it differs (`refresh_field`), which is exact only for derived, structural `PartialEq`: hash containers keep `clone_from`, because equal maps can iterate in a different order, and the keyword collections compare with `KeywordCollection::eq_in_order`, because `IndexMap` equality ignores order. `refresh_parity_snapshot` and `clone_for_parity_snapshot` list every `Card` field on purpose, so a new field fails to compile until it is added to both. Cloning every card for every decision, twice, was 86% of a game's time before this.

### Add a regression entry

After fixing a bug, lock the fix in. Add to `regression.json`:

```json
{
  "name": "descriptive_snake_case_name",
  "args": "--deck1 <deck> --deck2 <deck> --seed 42 --max-turns 20 --games 1"
}
```

Pick the smallest seed/turn budget that reliably triggers the bug. The matrix runs 3 seeds × 7 decks = 126 matchups, so one entry per regression is enough.

### Skip a known-divergent matchup

Edit `parity_ignore.json`. Every entry needs a written reason. Don't ignore a divergence to make CI green — investigate first.

## Conventions

- **Both engines share an RNG seed.** Anything that consumes randomness must be threaded through `game_rng` (Rust) and the matching `MyRandom` path (Java). New RNG callsites that drift cause every downstream divergence.
- **Card identity is by name, not id.** Internal IDs differ between engines. The comparator sorts by name.
- **Default mode takes one snapshot per turn, at untap.** A divergence reported at "T9 Untap" happened somewhere in turn 8. `--deep` snapshots every phase change, every priority change and every decision on both sides; `--localize` does that rerun for you.
- **The Rust action space asks Forge's castability check by default.** `--mana-probe forge` (the default) sets `GameState::action_space_mana_probe` to the port of `ComputerUtilMana.canPayManaCost`, which the Java harness's `ActionSpace` calls. That check pays greedily and refuses some payable costs: with two Forests and two Islands untapped, Dragonclaw Strike's `{2/G}{2/U}{2/R}` is refused, because the second Forest pays the generic half of `{2/U}` and the Islands cannot finish `{2/R}`. `--mana-probe autopay` runs the engine's own payment simulation, as the app does, which finds those payments. A divergence that goes away under `forge` and comes back under `autopay` is Forge's greedy check, not an engine bug.
- **The Java harness API surface is stable.** `forge-harness/` is ours, but its API is consumed cross-language; changing a method signature breaks every parity test. Add new methods, don't rename existing ones.

## When the harness itself is broken

If divergence reports look wrong (e.g. spurious differences in unrelated fields), suspect:

- A new field in `snapshot.rs` / `comparator.rs` that's non-deterministic across engines.
- A change to the Java harness that didn't propagate to the JAR (`yarn build:harness`). The Java cache key includes the jar, so a rebuilt jar reruns Java once and an unchanged one does not.
- A `FORGE_*_TRACE` env var leaking ordering information into the snapshot.
- A divergence whose headline is `snapshot.exists: Rust=present Java=missing`, with the two decision logs agreeing right up to it: Forge threw. `Main.runGame` catches the exception, prints `[harness] Game error: …` to stderr and ends the game, and the runner drops harness stderr, so the report shows only a Java side that stopped. Rerun that matchup against the jar directly to see the stack trace — the report's `deck1`/`deck2` strings are valid `--deck1`/`--deck2` arguments, and `--forge-home forge/forge-gui/` is what the runner auto-detects. The trace names the effect, and the cause is usually a `PlayerController` method the harness answers where Forge's own controllers do extra work (`DividedAsYouChoose$` was one).
- Every game `ERROR` with `Java server closed stdout (crashed?)`: the JVM died. The error ends with the server's last five stderr lines (`JavaServer::crashed`), which the stderr filter otherwise drops; without `JAVA_HOME` or an OpenJDK on `PATH` the macOS `/usr/bin/java` stub prints `Unable to locate a Java Runtime`. A run that hits the Java cache starts no JVM, so a wrong environment only shows once the jar changes.

Rebuild the harness and rerun before assuming the engine is wrong.
